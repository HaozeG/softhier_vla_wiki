# Unitree Go2 and G1: how the compute is arranged

## Summary
Unitree's public pages describe the compute of its quadruped (Go2) and humanoid (G1) as an "8-core high-performance CPU" that runs the closed motion-control software, with an optional external NVIDIA Orin module for users on the EDU versions. Third-party analysis identifies the Go2's main SoC as an RK3588S. The vendor's marketing pages give no NPU figures, control rates or software map, but its open example code does: it shows that the built-in motion program must be released before user code can send motor commands, that the example motor-command loop runs at 500 Hz and the example walking policy at 50 Hz, and that the second computer (PC2) hosts camera and hand services for teleoperation. Those rates are the example code's settings, not measured properties of the built-in controller.

## Details
- **Go2 (vendor page):** the AIR variant lists no CPU; PRO, X and EDU list an "8-core high-performance CPU" for advanced mode, AI mode and 3D LiDAR mapping. The EDU offers "Orin (40–100 TOPS)" as an optional high-compute accessory, not integrated. Sensors: 4D LiDAR (360° × 96°, 0.05 m minimum range) on all variants, wide-angle camera, optional depth camera on EDU. Battery 8000 mAh (about 1–2 h) or 15,000 mAh on EDU (about 2–4 h). No NPU or control-frequency figures. Secondary development is marked for X and EDU.
- **Go2 (third-party teardown of the firmware, DarkNavy):** "The GO2 robot dog utilizes the RK3588S chip." Linux firmware with a U-Boot bootloader; modules communicate through DDS (CycloneDDS topics); a `webrtc_bridge` talks to the phone app, MQTT delivers OTA updates, Bluetooth handles setup. The article does not say which module does motion control, the number of boards, memory, or control rate.
- **G1 (vendor page):** basic model has an "8-core high-performance CPU"; EDU offers "Orin" and other high-compute modules as an optional accessory (no TOPS on the page). 23 DoF standard, 23–43 on EDU (dexterous hand options), about 35 kg, 9000 mAh battery, about 2 h runtime, depth camera plus 3D LiDAR, 4-microphone array; the page mentions the "UnifoLM" model platform without deployment details.
- **G1 EDU (documentation mirror, quadruped.de):** two computers. The motion-control unit (PC1) "is exclusively dedicated to the Unitree motion control program and is not accessible for public use". The development unit (PC2) is a Jetson Orin NX with 8 Cortex-A78AE cores, 16 GB memory and 2 TB storage (the vendor's older material and retailers quote 100 TOPS; NVIDIA lists the 16 GB module at 157 sparse INT8 TOPS, see [Jetson specs](nvidia-jetson-platform-specs.md)). A LIVOX MID360 LiDAR and D435i depth camera connect through the neck interface; joints are custom motors (120 N·m peak, dual encoders); dexterous hands use RS485.
- **How user policies reach the robot (open repository `unitree_rl_gym`):** locomotion policies are trained with Isaac Gym and PyTorch (`rsl_rl`), checked in MuJoCo (sim2sim), exported as small MLP or LSTM policies (`policy_1.pt`-style files), and run on the real robot through a Python deploy script that takes a network interface, or a C++ path using LibTorch. Supported robots: Go2, G1, H1, H1_2. The repository states no compute requirement; the policy is a TorchScript model (`torch.jit.load`) called on the CPU in the deploy script, so a policy of this size needs no accelerator.
- **Market report (secondary):** a press release describing a research report lists the Unitree A2 quadruped (Aug 2025) as an Intel Core i7 "brain" for secondary development and AI deployment plus an 8-core CPU "cerebellum" ([architecture reports](robot-controller-architecture-reports.md)).

**Software placement and rates from open example code (first-party code; example settings, not the built-in controller's rates)**
- **Built-in motion program versus user control.** In `unitree_rl_gym` the robot is put in zero-torque mode, then the remote's L2+R2 enters "debugging mode" (joints damped), and an external computer connected by Ethernet runs `deploy_real.py {net_interface} g1.yaml`. In the `unitree_sdk2` G1 low-level example, the program first loops on a motion-switcher client (`CheckMode` / `ReleaseMode`) "to shutdown motion control-related service" before it publishes to `rt/lowcmd`. So the built-in controller and user low-level control are mutually exclusive, which matches the closed motion-control computer (PC1) described above.
- **Message path.** User code reads `rt/lowstate` and writes `rt/lowcmd` over DDS (a publish/subscribe message bus) with a CRC on each message; commands carry position, velocity, torque feed-forward and stiffness/damping gains per motor (29 motors on the G1 example).
- **Rates.** The `unitree_sdk2` G1 example sets `control_dt` to 2 ms with 2000 µs recurrent threads for control and for command writing, and its state handler treats every 500 callbacks as one second, i.e. state at about 500 Hz. `unitree_rl_gym` sets `control_dt: 0.02` (50 Hz) for G1, H1 and H1_2, with 47 observations and 12 actions for the G1; its loop paces itself with `time.sleep`, so the achieved rate is at most 50 Hz.
- **Where the policy runs.** The `unitree_rl_gym` README uses an external computer over Ethernet. A community C++ binding (`unitree_cpp`, third-party README) says the official Python SDK "often suffers from serious performance issues, making it difficult to achieve real-time deploy with built-in Jetson pc2", and reports, from a test with the AMO policy on G1 PC2, a cost of control of 3,871 µs per hit for `unitree_sdk2_python` versus 40 µs for its binding. So user control code does run on the built-in Jetson in practice, and the Python SDK's overhead matters at these rates.
- **What PC2 hosts (`xr_teleoperate`, first-party).** Teleoperation runs on a host PC with a default `--frequency` of 30 Hz; PC2 (192.168.123.164) runs the camera image service (`teleimager`, with a WebRTC option) and hand-control services (Inspire, BrainCo, Dex1-1 gripper); a `--headless` option is for running the program on PC2 itself. With `--motion` the teleoperation program runs alongside the robot's own motion control program (Regular mode only), otherwise the robot is in debug mode.
- **Not found in these sources:** the built-in controller's own loop rate, NPU capability of the built-in processor (a third-party teardown names the RK3588S for the Go2), and any rate for the Go2 (the examples read cover the G1, H1 and H1_2).
